## 做对了什么

- **fork 的决定让改造面收敛**。真正动过的只有状态机、提示词、提醒、overlay 门禁四处；
  replay / 信封 / 渲染钩子几乎原样保留，因此兼容性不需要"重新发明"。
- **先写 spec 再补测试**。四份 spec 的 WHEN/THEN 直接变成了五个测试文件的断言，
  没有出现"测试在测实现细节、spec 在说另一件事"的漂移。
- **把"无上界"当否决理由**。oracle 给的"无上限 + pause 工具"方案看起来更灵活，但成本不可预测；
  用硬上限换来的是"最多多三轮"这个可写进 spec 的确定承诺。
- **修 bug 时先问"这个槽位是什么语义"**。`getActiveRenderSession()` 名字里就写着"render"，
  却被用来读会话任务；这一处比任何测试都更早说明模式兼容是"语义问题"而不是"参数问题"。

## 踩过的坑

| 坑 | 表现 | 教训 |
| --- | --- | --- |
| 读错槽位 | `agent_before_settle` 读前台渲染槽，RPC 第二会话永远收不到提醒 | 单测只在 tui 语义下写，bug 就永远不暴露；**模式相关逻辑必须逐模式写测试** |
| 文档与源码不一致 | `docs/` 写"`waiting` 理由另起一行"，实际是同行追加 `⏸` | 写 spec 时逐条对着源码复核，比"再读一遍文档"更有效 |
| 测试计数笔误 | README 写 "131 tests"，实测 78（后来又变 149） | 计数类断言要么别写，要么从实测输出复制 |
| 预热无门禁 | 工厂作用域无条件 `setTimeout`，无头模式白 import overlay | "延迟执行"不等于"廉价执行"；timer 调度点也要过模式门禁 |
| 假 ctx 不完整 | 漏 `sessionManager.getBranch` 导致 `session_start` 直接抛错 | 测试桩应从真实调用点反推字段，而不是从"我以为需要的字段"拼 |

## 如果重来

1. 一开始就写 `test/modes.test.ts` 的骨架，再写实现——模式的四条分支是最容易被"默认 tui"
   掩盖的地方。
2. 把 `resolveMode` 放进第一个 commit。它是唯一的策略分叉点，越晚引入，越多代码默认
   假设 `tui`。
3. 从一开始就用 `openspec/changes/` 走变更流程（本次是先写 living spec、后补归档），
   这样 delta 与 living spec 天然一致，归档时不必反向推导"变更前是什么"。

## 遗留

- `waiting` 与提醒的结合还缺一个真实场景验收：任务 park 后外部事件到达（CI 绿了），
  模型是否会主动把状态改回 `in_progress`——这取决于提示词引导，而不是代码，需要
  实机观察几轮再决定要不要加强 guidelines。
- 多语言：`src/i18n.ts` 的桥已就位，但只提供英文文案。需要时补 `locales/` 即可，
  不需要改调用点。
